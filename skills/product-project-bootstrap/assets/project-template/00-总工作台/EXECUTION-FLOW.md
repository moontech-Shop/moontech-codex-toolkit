# 开工、建设与验收

## 1. 建立当前基线

总台检查已有资料及真实开发目录，记录商店、域名、主题角色/ID、仓库分支和当前文件负责人；技术位置只在 PROJECT-INDEX 中维护，STATUS 引用它。已有源码保留原位置，不因为模板建立了 Theme 目录就迁移或另建一套。

PROJECT-BRIEF 记录任务模式、范围、保留项及采用的标准文件路径/版本。已有可用标准直接引用，不复制多份互相竞争的规则。默认采用本项目 `06-QA与发布/QUALITY-STANDARD.md` v1.2；来源与冲突处理见同目录 STANDARD-SOURCES，结果只记 QA-CHECKLIST。用户指定的标准差异记入 PROJECT-BRIEF，不依赖其他项目绝对路径。

## 2. 依据任务模式规划

- 严格复刻：先填 REFERENCE-MAP 的双端模块与交互映射，再实施。未经用户要求不删减、重排或改成概述。
- 只改美术：保留内容、信息结构和行为，只改已授权的表现部分。
- 重新设计：记录目标、内容范围和选定视觉方向后开展设计。
- 资料不足的声明单独标记待补，不因此默认删除整个模块，也不把未验证内容作为本品牌事实发布。

## 3. 建立视觉基准并实施

总台维护 VISUAL-BASELINE，页面工作台按基准制作。已有选定方案直接沿用；新方向默认2–3张风格卡，并为推荐方向制作至少一套完整Home手机/PC方案。选定后落实框架和Home初版，再以少量问答逐步补全。严格复刻直接遵循参考，不探索替代风格。各模块分别考虑手机/桌面的顺序、裁切、折叠、滑动和 CTA 行为。

## 4. 按影响范围集成

总台处理共享代码及远端上传。上传前获取目标文件最新版本，对照工作开始时的基线合并；发现重叠修改先协调，不整份覆盖旧副本。页面任务提交文件与证据，由总台审查集成。A/B 快照无法修改时明确遗留范围，不擅自重建测试或改变分流。

## 5. 验收与交付

按本次 CHANGE-RECORD 的原始需求验收，再按影响清单检查关联页面、版本、设备和动态刷新状态。相关证据使用 QA-CHECKLIST 的记录格式。远端上传后回读核对并检查实际页面；技术通过不能替代视觉或交易通过。

总台将不同完成状态分别写入 STATUS；失败项修复后复验，暂不能验证的明确记录。页面工作台把证据和待办交给总台。已有授权不反复询问，仅对确实缺少授权的动作停下。
